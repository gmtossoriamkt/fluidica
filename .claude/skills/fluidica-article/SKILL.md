# Статья для fluidica.ru: от строки контент-плана до PR

Работаешь в репозитории fluidica.ru (GitHub `gmtossoriamkt/fluidica`). Цель - достоверная, полезная лаборатории статья, опубликованная через PR. В `main` напрямую не пушишь никогда: публикация = merge PR владельцем (или тобой по его прямой команде). Пуш в рабочую ветку `blog/*` разрешён без подтверждения. Деплой не меняешь: сайт публикует GitHub Pages из `main` как есть; что не публикуется - перечислено в `_config.yml`. Сначала прочитай `CLAUDE.md` - его правила (бренд-токены, только русский, латиница в адресах, prefers-reduced-motion) обязательны и здесь.

Python может называться `python3` или `python`; скрипты лежат в `scripts/` и запускаются из корня репозитория.

## 0. Выбор задачи

1. Переведи в `done` все строки `content-plan.csv` со статусом `pr`, чьи PR уже смержены: `gh api "repos/gmtossoriamkt/fluidica/pulls?state=closed&per_page=50" --jq '.[] | {number, merged_at, head: .head.ref}'` (смержен - если `merged_at` не пустой) или по наличию `blog/<slug>/index.html` в `origin/main`. Эти правки включи в PR текущей статьи.
2. Если в запросе указан номер статьи - бери его, иначе первую строку со статусом `todo` по порядку `num`. Статусы: `todo` → `in-progress` → `pr` → `done`. Строки `skip` не берёшь никогда (причина - в `note`; менять решение может только владелец).
   Автоматически не делаешь (оставляешь `todo`, переходишь к следующей и называешь в итоге): `format` = «Кейс» - нужны реальные данные проектов, придумывать нельзя.
   Колонки: `title` - рабочая тема (в плане много шаблонных формулировок с ошибками согласования: «Как выбрать микрофлюидика» - H1 пишешь грамотно и по смыслу), `main_keyword` - целевой запрос, `format` - Обзорная / Гайд / Инструкция / Сравнение / Обзор / Прикладная / Разбор / Разбор цены / Подборка / Чек-лист / FAQ, `funnel` - TOFU/MOFU/BOFU, `internal_link` - куда вести читателя (раздел каталога или блог), `note` - пометки владельца.
3. Создай ветку от свежего main: `git fetch origin main && git checkout -b blog/<num>-<короткий-слаг> origin/main`. Если ветка создана автоматически с другим именем - работай в ней, но укажи номер в заголовке PR. Поставь статус `in-progress`.
4. Если есть `factcheck/<num>.md` - это фактчекинг редактора: учти замечания, заголовок и структуру. Он тоже вторичный источник - его утверждения проверяются.
5. Если фактчекинга нет - сделай его сам до текста: какие понятия в теме смешиваются (лабораторный насос ≠ медицинский инфузионный; точность ≠ повторяемость; калибровка ≠ поверка ≠ валидация; расход по паспорту ≠ расход в вашей системе; открытый проект ≠ готовый прибор), какие тезисы рискованны, какой заголовок не обещает лишнего. Если тема о том, чего нет в каталоге Fluidica (центрифуги, ПЦР, спектроскопия и т. п.) - пиши честный обзор для лаборатории и не придумывай товаров и услуг Fluidica.
6. Проверь дубли: `grep -ril "<ключ>" blog/*/index.html` и заголовки карточек в `blog/index.html`. Если тема уже раскрыта (см. `note`, например у № 22) - не публикуй вторую: открой PR как draft с предложением (дополнить старую статью или развести интенты) и пометкой «нужно решение человека».

## 1. Исследование

- **Первоисточники** - то, на что ссылаешься в «Источниках»: документация и руководства производителей (Watson-Marlow, Masterflex/Cole-Parmer, Ismatec, WPI, Ossila, Elveflow, Darwin Microfluidics, Microlit, Blue-White и т. п.), научные статьи (PMC/NCBI, Scientific Reports, HardwareX, PLOS ONE, Micromachines), репозитории и публикации открытых проектов (GitHub, статьи авторов). Нормы РФ (ГК РФ, 44-ФЗ, 223-ФЗ, 102-ФЗ, ПП № 719 и др.) - по тексту акта: zakonrf.info; pravo.gov.ru / publication.pravo.gov.ru из облака обычно недоступны - не больше одной попытки; если первоисточник недоступен - kontur-extern.ru/info/normativ, kormed.ru (указывай, по какому сайту сверено, и «актуальную редакцию сверяйте по официальному источнику»).
- **Статьи сайта fluidica.ru - не подтверждение.** Сверка со своими статьями нужна только для согласованности и ссылок; факт, который есть только на сайте, проверяется заново.
- **Вторичные источники** (новости, обзоры, страницы магазинов, фрагменты поисковой выдачи) - только подсказка. Факт, найденный только в них, подаётся мягко («по данным поставщика…») или не подаётся. Если страница прочитана по фрагменту выдачи, а не целиком, - так и напиши в «Источниках».
- **Что уже выверено на сайте (не нарушай):**
  - характеристик насосов Fluidica, которых нет в `data/products.json` и карточках товаров, не приводить (например, «точность ±1%» не подтверждена - в статьях её нет; решение по главной ждёт владельца);
  - цены конкурентов - только если их публикует производитель; Chemyx Fusion 100-X/200-X - «call for pricing»; ориентиры по рынку - коммерческие предложения;
  - Poseidon (Booeshaghi et al., Sci Rep 2019): «менее $400 за систему из трёх насосов и микроскопа»; разбивки «$175» нет в источниках;
  - шаговый двигатель: погрешность шага невелика (порядка нескольких процентов шага) и не накапливается; «физика гарантирует одинаковый шаг» - завышение; микрошаг сглаживает подачу, но не повышает позиционную точность;
  - Pearce, HardwareX 2020: ~87% экономии (89% с Arduino, 92% с RepRap, 94% с обоими) - уточнять вариант;
  - медицинские изделия (например, ИНШ-01) - с оговоркой: пригодность для лабораторного дозирования определяет производитель и применение;
  - ПП РФ № 719 - «в действующей редакции»; применимость зависит от категории оборудования и условий закупки.
- Если на сайте нашлась ошибка или устаревшая дата в чужой статье - не правь её в этом PR, внеси в отчёт.

## 2. Текст

Формат - как в существующих статьях (образец - статья из первой карточки `blog/index.html`):
- H1 - грамотный заголовок. Тег-метка в `eyebrow` - по типу: Основы, Обзор, Гайд, Инструкция, Сравнение, Разбор, Цены, Чек-лист, Подборка, Импортозамещение, Для новичков, Автоматизация, Микрофлюидика, FAQ.
- `hero-sub` - одно-два предложения о том, что получит читатель. В `article-meta`: дата публикации, «~N мин чтения» (≈ 1000 слов на 7-8 минут), кластер (например, «Перистальтические насосы»).
- Вводные абзацы и абзац **«Как читать материал»**: на что опирается статья (документация производителей, а не независимые испытания), что примеры моделей не переносятся на другое оборудование, что статья о лабораторном, а не медицинском оборудовании.
- Разделы H2 (H3 внутри при необходимости); списки `<ul>/<ol>` с пунктами в `<li><span>…</span></li>` (для блоков `.checklist` это обязательно); таблицы `table.compare` там, где сравнение; практический порядок действий или чек-лист; типичные ошибки.
- Ссылки на 3-6 своих статей по ходу текста (обычные `<a href="/blog/<slug>/">`) и на раздел каталога из `internal_link`.
- H2 «Главное» - короткий вывод. H2 «Источники» - абзац-оговорка (на что опирается статья, что не проверялось) и нумерованный список: ссылка `rel="noopener" target="_blank"`, название, одно предложение - что это за источник и что из него взято, чья это позиция (производитель, поставщик, научная статья).
- Формат «FAQ» - вопросы под `<h3>N. Вопрос?</h3>` с ответом абзацами и FAQPage в JSON-LD с теми же вопросами дословно (см. `blog/faq-peristalticheskie-nasosy-chastye-voprosy/`). В обычных статьях FAQ-блок не нужен.
- Блок `article-cta` (`data-reveal`): заголовок-вопрос, одно предложение, кнопка `<a href="/#request" class="btn-primary">Оставить заявку</a>`.
- «Читать дальше» (`.related-links`): 5-8 ссылок - близкие статьи, раздел каталога, `/blog/`.

Правила содержания:
- Каждый конкретный факт (число, диапазон, модель, функция, требование, дата, норма) - только если подтверждён первоисточником. Нет подтверждения - обобщи или убери.
- Не обещай результат («подойдёт без доработок», «точность гарантирована») - пиши условия и что проверить измерением.
- Без выдуманных характеристик, цен, сроков и кейсов Fluidica; про каталог - только то, что есть на карточках.
- Тон инженера-практика, без воды; русская типографика (« », —); только русский язык (латиница - для названий моделей, единиц и англоязычных названий источников).
- Объём - как у статей того же формата (обычно 1200-2500 слов; FAQ и pillar - больше).

## 3. Шаг 0 - сверка

Перед сборкой страницы пройди по тексту и для каждого конкретного факта отметь: **подтверждено** (источник, раздел/страница) / **исправлено** (было → стало) / **убрано** / **не проверено** (почему). Это отчёт для описания PR. Если не проверен ключевой для статьи факт - PR будет draft.

## 4. Сборка страницы

Генератора статей в репозитории нет: страница собирается по образцу последней опубликованной статьи, а служебные части проверяют и дополняют скрипты.

1. Скопируй `blog/<slug-первой-карточки>/index.html` в `blog/<новый-slug>/index.html` и замени содержимое: `<title>` («<короткий H1> - Fluidica», не длиннее 65 символов; в отчёте - длина), `meta description` и `og:description` (110-160 символов, не повторяют соседние статьи), canonical и `og:url` = `https://fluidica.ru/blog/<slug>/`, `og:title`; JSON-LD `Article` (headline = H1, description, `datePublished` = `dateModified` = сегодня, `mainEntityOfPage`) + `BreadcrumbList` (Главная → Блог → короткое имя) + `FAQPage` для формата FAQ; хлебные крошки, `eyebrow`, H1, `hero-sub`, `article-meta`, тело статьи, CTA, «Читать дальше». Шапку, футер, стили и скрипты внизу страницы оставь как в образце. Slug - латиница (транслит), со слэшем на конце в ссылках.
2. Служебные блоки (идемпотентны, повторный запуск ничего не меняет): `python3 scripts/add_icons.py`, `python3 scripts/add_analytics.py`, `python3 scripts/self_host_fonts.py`, `python3 scripts/add_header_contacts.py` - затем у каждого `--check` должен показать 0.
3. Карточка - первой в `<div class="blog-grid">` в `blog/index.html` (у самой сетки `data-reveal` нет и не добавлять): ссылка, дата («27 ноября 2026»), «~N мин чтения», метка, заголовок = H1, выдержка = meta description. Счётчик «N статей» в `.section-desc` увеличь на 1 с правильным склонением (1 статья, 2-4 статьи, 5-20 статей, 21 статья…). Карточки - от новых к старым.
4. Страницы решений и подборок: если статья по теме страницы - добавь slug в `articles` нужной записи `data/pages.json` (страница решения - не больше 6-7 статей) и запусти `python3 scripts/build_pages.py`, затем `--check` = 0.
5. Обратные ссылки: в 2-4 тематически близких статьях добавь ссылку на новую статью в «Читать дальше» (после последней ссылки на статью блога, перед ссылками на каталог). В блоке не больше 8 ссылок; если он полон - замени самую слабую по теме и проверь (`grep -rl 'href="<url>"' --include=*.html .`), что на заменённую страницу остаются другие входящие ссылки; что заменено - в отчёт. Это несодержательная правка: `dateModified` и плашку не трогаешь.
   Если меняешь содержание опубликованной статьи (факты, формулировки, разделы) - добавь в `article-meta` после даты `<span>Обновлено: <дата></span>` (если плашка уже есть - обнови дату), `dateModified` в JSON-LD = сегодня; `datePublished` не трогаешь. Такие правки - только если они нужны для новой статьи; найденные ошибки старых статей - в отчёт.
6. Sitemap: `python3 scripts/check_sitemap.py --fix` (статья встанет перед записью `/blog/`), затем последним шагом перед коммитом `python3 scripts/check_sitemap.py --lastmod`. lastmod в этом репозитории не правится вручную: скрипт ставит дату последнего коммита страницы (для изменённых сейчас - сегодня), поэтому у статей с обратными ссылками lastmod тоже обновится - это ожидаемо.

## 6. PR

1. Статус в `content-plan.csv` → `pr`, в `url` - `https://fluidica.ru/blog/<slug>/`.
2. Коммит (сообщение: `Статья <num>: <тема>`), `git push -u origin <ветка>` - только после зелёных проверок (`&&`). В `main` - никогда.
3. PR в main через `gh api` (`gh pr create` в облачной сессии не работает); описание - из файла во временной папке по шаблону `.github/pull_request_template.md`:
   `gh api repos/gmtossoriamkt/fluidica/pulls -f title="blog: <num> <тема>" -f head=<ветка> -f base=main -F body=@<файл>` (для черновика добавь `-F draft=true`).
   В описании: адрес, title (длина) и description (длина), ключевые запросы; отчёт шага 0; что не проверено и почему; изменённые файлы и статьи с обратными ссылками (что заменено); результаты проверок; адреса для переобхода в Яндекс.Вебмастере (новая статья, `https://fluidica.ru/blog/`, статьи с обратными ссылками, пересобранные страницы решений).
4. **Draft PR**, если: ключевой факт не проверен и смягчить нельзя; тема дублирует опубликованную; нужна правка содержания чужой статьи; нужен выбор владельца (заголовок, позиционирование, утверждения о продуктах Fluidica). В начале описания - «Нужно решение человека: …».
5. Ветки не удаляй (удаляются после merge). PR не мержишь без прямой команды владельца.
6. В конце - короткий итог со ссылкой на PR и отчётом шага 0.
7. После merge (если мержишь по прямой команде владельца) деплой идёт сам: GitHub Pages публикует `main`. Ничего в настройках деплоя не меняешь.

## Если что-то пошло не так

- Тема в плане сформулирована некорректно → напиши статью с исправленным заголовком и объясни в PR.
- Первоисточник по ключевому тезису недоступен, а смягчить нельзя → draft PR с пометкой «нужно решение человека».
- Сеть до нужного сайта закрыта окружением → не обходи; отметь «не проверено (сайт недоступен из окружения)» и назови хост в PR.
- Скрипт проверки падает на чужой странице (не из этого PR) → не чини попутно; открой PR как draft и опиши проблему.
